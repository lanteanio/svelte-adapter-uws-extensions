# Factory option checks

[Package overview](../README.md) | [Migration guide](../MIGRATION.md#factory-options-refuse-values-they-cannot-honor) | [Release history](../CHANGELOG.md)

Every factory checks its options when it is called, on the same terms as the adapter checks its own:

- **An unrecognized key warns and is ignored.** One `console.warn` names every unknown key and, when one is close enough, the documented key it was probably meant to be: `[extensions] unknown createPresence option(s): hearbeat (did you mean 'heartbeat'?) - not recognized by createPresence and ignored. ...`. It never throws, so an options object written for a newer version still starts an older one. A factory constructed many times with the same options (a group per room) warns once for the same set of unknown keys, not once per call.
- **A recognized key with a value the factory cannot honor throws an `Error`** before any timer starts or any connection opens, naming the option, what it accepts and what it got: `redis presence: keyspaceNotifications must be true or false - got "false" (string).` A misshaped value is never read as "use the default", because most of them silently disabled what they configured: `autoMigrate: 'false'` ran migrations, `breaker: 'on'` failed on first use, `persistLeaseMs: '6000'` fell back to 6000 without a word.
- **`undefined` and `null` both mean "not set"** and take the default. The one exception is the pub/sub `systemChannel`, where `null` turns the health events off. Breakers and metrics registries accept any falsy value as "none", as they always did.
- **Options shared with the adapter's in-memory plugins read the same way.** Presence, cursor, groups and the rate limiter accept every value the adapter's in-memory plugin of the same name accepts for an option both read (for example presence `binary: 'false'`, a falsy presence or cursor `select`, cursor `throttle`, group `meta`, a fractional rate-limit `interval`), so swapping one for the other never meets a refusal only one of them makes. The values both accept also resolve the same way, defaults included (a group caps members at 1,000,000 unless told otherwise, and refuses a full group before calling `onJoin`; only a concurrent join that fills the group between that check and the atomic join, or the per-instance local member cap, leaves an `onJoin` call for a join that ends full). One behaviour differs on purpose: a rate-limit `keyBy` that returns a new object on every call gives each call its own bucket in the in-memory limiter, so nothing is limited, while the Redis limiter turns the key into a string and limits all such calls together. The one exception is presence `heartbeat: 0`. The in-memory plugin reads it as "no heartbeat"; the Redis presence refuses it, because each heartbeat also renews the Redis TTL of every local entry, and without it every present user would expire from the shared roster after `ttl` seconds.
- **Timer intervals stay within Node's timer range.** Node stores a timer delay in a signed 32-bit integer and turns anything above 2147483647 ms into a 1 ms loop, so an option that paces a timer refuses a larger value (for a seconds option, its millisecond equivalent; for a value whose fraction paces a timer, such as a lease renewed at a third of its length, that derived delay). Presence `heartbeat` and `topicThrottle` and cursor `throttle` and `topicThrottle` are shared with the in-memory plugins and follow the point above.
- **Lifetimes Redis receives as an expiry are whole milliseconds** (whole seconds where Redis takes seconds). Redis refuses a fractional PX or EXPIRE argument, so a value such as `ttlMs: 1500.5` used to fail every write that set it. The rate limiters round their expiries up instead, so a fractional interval or block works there.

TypeScript declarations list each factory's accepted keys; the checks give a JavaScript caller the same answer at startup.
